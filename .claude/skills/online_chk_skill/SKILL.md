# 慧礼记上线前检查（online_chk_skill）

目标：对当前代码做一次「能否上线」的全面审查，给出 go / 有条件 go / no-go 结论、必须先做的事项和需要用户决定的问题，并以通俗中文发到微信（如果请求来自微信）。

## 0. 前置原则
- 只读：不改业务代码、不部署、不提交、不上传、不 push。审查结论只写进 agent 记忆。
- 用户既有决策不推翻，只提示风险：会员策略 B（保留「联系我们开通」）、暂不 push、存储保持「所有用户可读，仅创建者可读写」（宾客端读收款码、导出下载依赖它）、上线前先「清除全部测试数据」再「标记正式上线」。
- 发现「需要用户拍板」的问题用 A/B/C 选项并标推荐。

## 2. 并行委派两个只读审查（同一条消息里发出）
1. **code_review agent** —— 全面代码审查，九个维度逐一评分（1–5）并列问题（严重/高/中/低，含 file:line、影响、修复建议、工作量、是否阻断上线）：
   数据安全性 / 功能完整性 / UI 友好与兼容性 / 系统运行稳定性 / 用户体验 / 运行性能 / 后续扩展性 / 运行成本 / 上线前准备。
   必须特别核查：
   - 所有云函数 action 鉴权（新增 action 是否同时在 OWNER_ACTIONS 与 NEED 注册、仅本人/仅管理员）、_openid 伪造过滤、resolveCtx 失败即报错
   - 写账一致性：reqId 幂等、条件原子更新、批次、incBookStat 与读回失败、限流（takeSlot 分桶）与 rate_limits 清理
   - 宾客可见内容不泄露记账人身份与 openid；status 缓存键含 openid
   - 订阅消息：模板用途与标题是否一致（入簿模板、未收到模板、主家新礼金模板），一次性订阅额度
   - 内容安全覆盖所有展示给他人的文本与图片字段
   - 上线前检查（preflight / __meta 探测）是否有副作用
   - 运行成本与容量：按当前套餐额度（云函数并发 20、数据库 QPS 30、环境 QPS 500，如用户更新以新值为准）估算同时可承载场次与最先触顶环节
   - 剩余控制台/后台/真机事项，并对照管理员页「上线前检查」哪些已能自动看到
   完成后把结论追加到 code_review 审查记忆。
2. **ui_chk agent** —— 上线前界面检查（自上次 ui_chk 记录的提交起增量 + 全量抽查回退），三档输出：上线前必须修 / 建议修 / 可上线后处理；附待真机确认清单。重点：审核员路径、空态/错误态、白事与机构模式用词、非红主题、按钮字数（showModal ≤4 字、success toast ≤7 字、actionSheet ≤6 项）、安全区与自定义 tabBar、小屏与大字体、键盘遮挡、下拉刷新与弹层。完成后追加 ui_chk 记忆。

两个 agent 的提示都要写明：只读、HEAD 提交号与版本号、用户既有决策、需要输出「给非技术用户的通俗中文版」。

### 2.1 隐私合规专项（两个 agent 都要查；2026-11-02 提审曾因「隐私政策默认自动同意」被拒）
- 不得默认同意：全项目不得出现「登录即表示 / 提交即表示同意 / 视为同意 / 默认同意」类措辞；登录页「我已阅读并同意《隐私说明》」勾选框每次打开都是**未勾选**（不得从本地记忆恢复勾选），未勾选时登录、头像、昵称都被拦截并弹窗让用户自主选择。
- 告知入口：所有收集个人信息的界面都要能看到《隐私说明》入口——登录页、宾客随礼 pay 页（只写告知，如「填写的姓名与礼金仅用于主家记账，详见《隐私说明》」，不写「提交即同意」）、宾客首页、「我的 → 帮助与隐私」（未登录可进）。
- 不要接管微信隐私授权：不得注册 `wx.onNeedPrivacyAuthorization` / 自定义隐私弹窗 / `__usePrivacyCheck__`（v3.84.0 自定义弹窗不出现导致头像昵称无反应，v3.84.1 已撤回）；头像昵称等由微信官方弹窗处理。
- 隐私说明正文与实际行为一致：设备权限（相册仅写入、选图含收款码与封面照片、摄像头扫码、蓝牙、剪贴板仅写入）、头像上传云存储、内容安全检测、订阅消息、谁能看到（主家、获授权记账人/礼台人员、家人；宾客本人看自己的记录）、保留与删除期限。
- 小程序后台「用户隐私保护指引」须与隐私说明页一致且已生效（含用户信息-昵称头像）；隐私说明改动后提醒用户同步后台指引。
- 提审备注：提醒用户写明隐私同意方式（主动勾选、未勾选不能登录）。

## 3. 汇总与核对
- 收到两份报告后，**自己核对**与事实不符的说法（例如「某云函数可能未部署」——对照本会话的实际部署记录；「测试失败」——对照第 1 步结果），在汇报里更正。
- 合并去重，按严重度排序，给出：
  - 总结论：go / 有条件 go / no-go
  - 各维度评分表
  - 上线前必须做（区分「需改代码」与「用户在控制台/后台/真机操作」）
  - 需要用户决定的问题（A/B/C + 推荐）
  - 容量与成本
  - 上线后待办
- 若有新的上线前阻断项或用户决策，更新项目记忆 `launch-readiness.md`。
